# Clicky tests

Run everything with:
```bash
./tests/run_all.sh
```

Requires `python3`, `jq`, and the `jsonschema` pip package (`pip install jsonschema`) - the last one is a dev-time test dependency only, not something the plugin itself needs at runtime.

## Why this exists

An audit of this repo found several places asserting things were "verified live" or "validated during development... see their header comments," with zero test/CI/mock infrastructure anywhere to back those claims - the header comments in question didn't actually contain any such statement, and there was nothing anyone (including a future Claude session) could re-run to check. This directory makes those specific claims either true and reproducible, or removes them. It's deliberately scoped to what's actually claimed elsewhere in the repo, not an open-ended "test everything" effort:

- `syntax/` - `bash -n` / `python3 -m py_compile` over every script in `skills/` and `hooks/`, plus `check_js_syntax.sh` over every `.js` file. The baseline sanity check.

  The JavaScript check is not a plain `node --check`, for three reasons established empirically rather than assumed. First, `node --check` **false-passes** a `.js` file containing ES module syntax with a real error in it (the same file named `.mjs` correctly fails), so every file is checked through a temporary `.mjs` copy. Second, workflow scripts open with `export const meta` *and* use a top-level `return`, a combination that is invalid in every standard parser mode - Acorn's `allowReturnOutsideFunction` (ESLint's `ecmaFeatures.globalReturn`) requires `sourceType: "script"`, which forbids `export` - so the checker mirrors the engine by dropping the `export` and wrapping the body in an async function, emitted without a trailing newline so reported line numbers still match the real file. Third, syntax alone is too weak: `phase("Scan")` misspelled `pahse("Scan")` is valid syntax that fails only at runtime mid-engagement, so ESLint's `no-undef` runs against the workflow globals declared in `syntax/workflow-eslint.config.mjs` (which doubles as executable documentation of the workflow engine's injected surface). ESLint is preferred, `node --check` is the fallback, and the output states which ran. `test_js_syntax_check.sh` proves both directions against fixtures, including the `node --check` false-pass case and line-number alignment.

  The globals in that config are **measured, not guessed**: `syntax/probe-workflow-globals.js` is a real workflow script that runs through the engine and reports `Object.getOwnPropertyNames(globalThis)` back. It spawns no agents and costs nothing, so re-run it after a Claude Code upgrade and regenerate the config. This mattered - the first hand-written version of the config listed 28 names when the real surface is 71, which would have falsely rejected any workflow using `setTimeout`, `TypeError`, `Symbol`, `Reflect`, or a typed array. Workflow scripts are identified by content (`^export const meta`), not by living under `workflows/`, so a workflow script kept elsewhere is still checked correctly.

  This check earned its keep on its first run, catching a live `process is not defined` crash in `workflows/pentest-parallel.js` that would have killed every fresh `/clicky:pentest-parallel` invocation before it reached a single agent.
- `prompt_injection/` - runs the real `skills/ai-llm-security-testing/scripts/prompt-injection-probe.sh` against a real local mock HTTP server (`mock_server.py`, stdlib only) and asserts its canary-detection logic actually works: every injected canary is detected against a naively-reflecting endpoint, zero false positives against a refusing one. Backs `skills/ai-llm-security-testing/SKILL.md`'s "Verified live against two mock endpoints" claim.
- `schema_validation/` - runs the real `sarif_convert.py`, `cyclonedx_convert.py`, and `aibom_convert.py` (all in `skills/report-generation/scripts/`) against fixtures, and validates their actual output against the real, published SARIF 2.1.0 and CycloneDX 1.5 JSON Schemas (vendored in `schemas/`, see `schemas/README.md` for provenance). Backs `skills/report-generation/SKILL.md`'s schema-validation claim.
- `finding_validator/` - fixture test for `skills/session-management/scripts/finding-validator.sh`'s Tier 1 mechanical trace cross-check, covering all three possible outcomes (`pass`/`fail`/`no_evidence`).
- `calibration/` - fixture test for `skills/session-management/scripts/attempt-aggregator.sh`, the mechanism behind `skills/htb-decision-tree`'s self-calibrated success rates. Hand-computed expected rates, plus a check that a service below the sample-size threshold correctly reports `insufficient_data` instead of a misleadingly precise number.
- `severity_review/` - fixture test for `skills/session-management/scripts/severity-review-logger.sh` (the write side of the Tier 3 severity-calibration feedback loop, see `agents/severity-analyst-agent.md`). The load-bearing check: a deliberately-wrong self-reported `slop_score` gets mechanically recomputed from the critique's own `findings[]`/`flags` data (hand-computed expected value) rather than trusted verbatim - same "don't trust a self-report, verify mechanically" posture `finding-validator.sh` already applies at Tier 1 - and `severity_critique.json` itself gets corrected in place so `commands/pentest.md` Step 11.2 reads the trustworthy number. A second case confirms an already-correct self-report is left untouched, with no spurious mismatch flag.
- `severity_calibration/` - fixture test for `skills/session-management/scripts/severity-calibration-aggregator.sh` (the read/aggregate side of the same loop), structurally identical to `calibration/`'s coverage of `attempt-aggregator.sh`: hand-authored `severity_review.jsonl` across an active and an archived session, hand-computed expected per-category/per-`review_mode` average deltas and direction counts, and the same `insufficient_data` floor below the sample-size threshold.
- `tls_scan/` - runs the real `skills/web-vulnerability-testing/scripts/tls-scan.sh`. The `openssl_fallback` path is tested against a real local self-signed HTTPS server (`mock_tls_server.py`, stdlib only) - real handshake, real certificate/hostname-mismatch parsing. The `testssl.sh`/`sslscan`/`nmap` paths (not installed wherever this test runs) are fixture-tested by shadowing those tool names on `PATH` with stubs that hand the script's own real parsing code canned tool output, so it's the actual normalization logic being exercised, not a reimplementation of it.
- `security_headers/` - runs the real `skills/web-vulnerability-testing/scripts/security-headers-check.sh` against a real mock HTTP server (`mock_server.py`) with a vulnerable endpoint (missing clickjacking headers, no CSRF token field, no `SameSite`) and a safe one (all present), asserting both are read correctly.
- `engagement_state/` - tests for `skills/engagement-state/scripts/*.sh`: that an attack-tree branch cannot be closed as `exhausted` without evidence (and that `untested` is a separate, non-interchangeable status), that coverage cannot be claimed `done` without evidence nor `skipped` without a reason, and that a `credential_attack` is refused unless all three preconditions (auth surface, username linkage, operator approval) carry evidence - including the partial-evidence case, which is the one that matters, since an agent that scraped names off a web page can satisfy two of the three. Also asserts every WSTG id and test name in the generated catalog matches the vendored official OWASP checklist verbatim, and that the ledger carries all 109 WSTG checks rather than a silent subset.
- `ssh_spray/` - end-to-end tests for `tools/ssh-spray.py` against a **real SSH server** (`ssh_test_server.py` speaks actual SSH-2: real KEX, real host key, real password auth - nothing about the client library is stubbed). Covers the distinction the tool exists for: exit 0 when a credential is found, exit 1 for a genuine clean negative where every candidate reached authentication, and exit 2 when anything was left `UNTESTED`. The server can drop connections pre-banner the way OpenSSH's `MaxStartups` does, so the suite proves both that a fully-throttled run is never reported as a clean negative and that a valid credential is still recovered through intermittent throttling.
- `mcp_gateway/` - test suite for `skills/mcp-gateway` (its own `run_tests.sh`, invoked from here). Covers `token_store.py` with real unit tests against real temp session directories; `scope_gate.py`'s `classify()` via fixtures, run as the same subprocess CLI call `server.py`'s `register_target` uses internally; `scripts/provision-venv.sh` with a real venv creation and a real `pip install`, plus a timing-verified skip on a second run when `requirements.txt` hasn't changed; `scripts/launch.sh`, confirming it provisions the venv correctly, keeps `provision-venv.sh`'s own stdout off the real MCP stdio channel, and survives two concurrent provisioning calls racing on the same data dir; and `server.py` itself via a live MCP protocol check (`live_server_check.py`) that launches it as a real subprocess and drives it over real stdio JSON-RPC - a real `initialize`, `tools/list`, and `tools/call` for all 8 tools (including `log_agent_boundary` - see "Phase 0 multi-CLI groundwork" in `server.py`'s docstring) including a real `create_session` bootstrap call, a real elicitation round trip, and confirmation that gateway-side tracing (`$SESSION_DIR/logs/trace.jsonl`) is correct and never leaks a raw target/credential value (including `register_target`'s own raw `target` argument, the one gateway input that isn't already a token) - plus `test_scope_enforcement_modes.py`, which drives the same real subprocess through the `scope_enforcement` enforce/warn/off switch, and `test_command_timeout.py`, which backs `execute_command`'s timeout contract against a real timing-out command: partial output produced before the deadline is returned rather than discarded, the result is banner-marked `RESULT INCOMPLETE` so a timed-out check can't be read as a clean negative, and the whole process group is killed so no orphaned scanner survives to keep hitting the target (verified by a backgrounded grandchild that never gets to write its marker file).
- `cli_targets/` - tests for `tools/generate-cli-targets.py`'s three CLI targets:
  - `test_opencode_generation.sh`: a drift check (no `opencode` binary needed - confirms the checked-in `.opencode/`+`opencode.json` actually match a fresh generation) plus, if `opencode` is installed, a live permission-resolution check against the real binary (`opencode debug agent <name>`) confirming every OpenCode built-in tool resolves denied and every intended gateway tool resolves allowed for a sample of generated agents, and that the real `clicky-gateway` MCP server connects. Fast and deterministic - not a re-run of the full live-model adversarial dispatch (an agent denied `bash` asked to run `whoami` had to use `clicky-gateway_execute_command` instead; a real recon-agent dispatch against `scanme.nmap.org` correctly found ports 22/80 open with all output properly redacted) that validated the design against a real model in the first place - see the multi-CLI portability plan's Phase 1 section for that record.
  - `test_codex_generation.sh`: a drift check plus TOML validity/structural assertions on every generated `.codex/agents/*.toml` (correct model pin, correctly-shaped inline `mcp_servers` struct, `caller=` convention present) via Python's `tomllib` - no live `codex` calls, since Codex has no free/fast static-introspection command the way OpenCode's `debug agent` is, and a real dispatch costs real API time (confirmed during development: several minutes on a cold gateway venv, even when working correctly). The full live verification - discovering the real model-pinning requirement (`gpt-5.6-sol` silently drops MCP tools via an open upstream bug, `gpt-5.4` doesn't), the real `mcp_servers` schema (array and boolean forms both rejected before the correct inline-struct shape was found), a real adversarial shell-denial test through an actual spawned subagent, and a real end-to-end scan against `scanme.nmap.org` with correctly tokenized/redacted output - was done manually once against these exact generated artifacts and is recorded in the generator's own doc comments and the multi-CLI portability plan's Phase 2 section.
  - `test_copilot_generation.sh`: a drift check plus frontmatter/structural assertions on every generated `.github/agents/*.md` (explicit `tools:` allowlist referencing `clicky-gateway`, the embedded `mcp-servers.clicky-gateway` block's confirmed-required fields, `caller=` convention present) plus confirmation the `.claude/skills -> ../skills` symlink is correct. No live `copilot` calls, same reasoning as the Codex suite. The full live verification - the workspace `.mcp.json` bug (`github/copilot-cli#3126`) that motivated embedding `mcp-servers` per-agent instead of using a shared workspace config, the real required `args`/`tools` schema fields (each caught by an actual Copilot CLI validation error), a real adversarial shell-denial test through the `--agent` flag, and a real orchestrator-to-leaf delegation via the `task` tool - was done manually once and is recorded in the generator's own doc comments and the multi-CLI portability plan's Phase 3 section.
- `setup_wizard/` - tests for `tools/clicky-setup.sh` (the setup wizard, see `docs/usage.md`'s Setup Wizard section) and `tools/advanced_agent_assignment.py`. Every AI-CLI/`nix`/`npm` binary the wizard can call is stubbed on `PATH` (`fake_bin/`, populated per-fixture) - same technique `tls_scan/` already uses for `testssl.sh`/`sslscan`/`nmap` - so this suite never touches the real `~/.clicky/`, `~/.claude/settings.json`, or `~/.codex/`, and never actually invokes Nix/npm/network, on any machine it runs on. Covers: nothing installed (both install-consent prompts declined, correct `tool_provisioning: none`, no settings sync attempted for undetected hosts), all 4 CLI hosts + Nix + Kalilix + Codex all present and working (the full apply path, including the `pluginConfigs.clicky.options` sync), Codex installed-but-unauthenticated (the clean `codex login` hand-off), and an idempotent re-run preserving a pre-existing custom config value. Found and fixed two real bugs this way before they ever shipped: an early manual (non-automated) test run once wrote to the real `~/.claude/settings.json` because only one of the two path overrides existed yet (fixed by adding `CLICKY_CLAUDE_SETTINGS_PATH`, now covered by this suite's isolation); and the advanced per-agent-model feature's generated Claude Code wrapper script originally used Python's `!r` repr for shell-quoting the `--agents` JSON payload, which breaks on the apostrophes real agent prompt text contains (fixed with `shlex.quote()`, verified via a real captured-argv round-trip test, not just a syntax check).

Nothing here is a general-purpose test framework - it's plain bash/python with manual assertions, matching the rest of this repo's style (no other dependency is added beyond `jsonschema`).
